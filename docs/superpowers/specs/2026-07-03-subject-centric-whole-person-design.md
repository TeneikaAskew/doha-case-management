# Subject-Centric Home & Whole-Person Depth — Design Spec

**Date**: 2026-07-03
**Status**: Approved (brainstorming complete)
**Builds on**: `2026-07-02-vetting-case-management-design.md` (portal architecture, design system, personas)
**Source vision**: `case management.md` (Whole Person View feature doc)

## Purpose

Lead the portal with the **subject** — the whole person — rather than the workload.
Add a subject-population home page, and deepen the case view so every claim is
traceable to its source: record checks drill down to what was actually checked,
alerts and checks link to realistic source documents (police report, credit-file
extract, SAR), every record names the data provider it came through, and the
whole-person worksheet becomes an interactive, evidence-linked assessment tool.

**Non-goals**: full SEAD A–M grid on the case page (flagged-only stays); replacing
the persona Dashboard (it remains, at `/dashboard`); risk-score recalculation from
worksheet ratings; any backend.

## Decisions (locked with user)

| Decision | Choice |
|---|---|
| Home page | **New "Subjects" page at `/`** (default landing). Dashboard keeps its persona-aware content, moves to `/dashboard`, stays in nav. |
| Worksheet | **Assess + evidence links**: expandable factors, AI draft, evidence chips, adjudicator Favorable/Neutral/Concern rating + note, persisted in demo state. |
| SEAD grid | Not added — flagged guidelines only, as today. |
| Documents | **Realistic typed documents** — per-type schemas and viewer layouts, generated per subject by `data_gen`. |
| Architecture | **Data-first**: extend `data_gen` + case JSON schema; UI reads generated static JSON. No inline mock objects in components. |

## 1. Subjects home page

**Route/nav**: `/` → new `SubjectsHome` page; nav order: **Subjects** (FiUsers),
Dashboard (`/dashboard`), Case queue, CV alerts, Data providers, Analytics.
Existing deep links and tests that assume Dashboard at `/` update accordingly.

**Content, top to bottom** (all derived from `subjects.json` + `alerts.json`,
respecting `demo.alertStates` overrides the same way Dashboard does):

1. **KPI band** (5 KPI cards):
   - Total subjects
   - Enrolled in continuous vetting (`cvEnrolled`)
   - Initial vetting backlog (stage `INITIATION` or `INVESTIGATION`)
   - Awaiting adjudication (stage `ADJUDICATION`)
   - Subjects with open alerts (alerts not `ADJUDICATED`/`CLOSED`, after demo-state overrides)
2. **Vetting pipeline strip**: one segment per lifecycle stage with subject count
   (Initiation → Investigation → Adjudication → Continuous vetting). Clicking a
   segment goes to the case queue pre-filtered to that stage.
3. **Risk distribution**: single horizontal segmented bar of AI-risk bands
   (low < 40, moderate 40–74, high ≥ 75 via `riskBand`), with counts and legend.
   Plain CSS flex segments (no chart library needed).
4. **Needs attention**: top 5 subjects ranked by (status `ACTION_REQUIRED` first,
   then `NEEDS_REVIEW`) → open-alert count → risk score. Rendered as subject
   cards: name, position, stage pill, status pill, risk dial (reuse case-header
   pattern at small size), flagged guideline chips, open-alert count. Click → case detail.
5. **Subject directory**: `DataTable` of all subjects — columns: subject
   (name + position), tier, stage, status, AI risk, CV enrolled, open alerts,
   flagged guidelines. Text search (name/position) + filters (stage, CV enrolled,
   has open alerts). Row click → case detail.

**New files**: `pages/SubjectsHome.jsx`, styles appended to `pages.css`,
`__tests__/subjectsHome.test.jsx`.

## 2. Record checks with drill-down (Investigation tab)

Case JSON `investigation.coverage` is **replaced** by `investigation.recordChecks`
(generator + all case files + tests migrate; no dual support):

```json
{
  "item": "Police report retrieval (2026 arrest)",
  "status": "COMPLETE | PENDING | NOT_REQUIRED",
  "provider": "State & local courts",
  "requestedDate": "2026-06-24",
  "completedDate": null,
  "scope": "Chesapeake PD incident report for 2026-06-21 DUI arrest",
  "resultSummary": "Report requested from Chesapeake PD records division; awaiting response.",
  "documentUrl": "documents/SUBJ-002/police-report-26-44812.json"
}
```

`documentUrl` is null until the check is COMPLETE and a document exists.

**UI**: the coverage checklist becomes expandable rows (reuse
`CollapsibleSection` pattern): closed row = item + status badge (as today);
expanded = provider source chip, requested/completed dates, scope ("what was
checked"), result summary, and a "View document" button opening the typed
`DocumentViewer` inline when `documentUrl` is set.

## 3. Realistic typed documents

**Storage**: `portal/public/data/documents/<SUBJECT-ID>/<doc-slug>.json`,
generated by a new `data_gen/documents.py`. The shared DOHA decision stays at
`documents/doha-record.json`.

**Envelope schema** (all types):

```json
{
  "docType": "POLICE_REPORT",
  "title": "Arrest report 26-44812 — Chesapeake Police Department",
  "provider": "State & local courts",
  "receivedDate": "2026-06-23",
  "subjectId": "SUBJ-002",
  "fields": { "...docType-specific key-values..." },
  "sections": [ { "heading": "Officer narrative", "body": "..." } ]
}
```

**Document types and their `fields`**:

| docType | fields | sections |
|---|---|---|
| `POLICE_REPORT` | agency, reportNumber, incidentDate, location, charges[], arrestingOfficer, bookingNumber, disposition | Officer narrative |
| `CREDIT_REPORT` | bureau, accountName, accountNumberMasked, accountType, balance, pastDueAmount, daysPastDue, dateReported, paymentStatus | Account history summary |
| `SAR` | filingInstitution, sarNumber, filingDate, activityPeriod, totalAmount, transactionCount, transactions[] (date, amount, type) | Narrative |
| `RAPBACK_NOTIFICATION` | notificationId, triggerEvent, arrestDate, agency, ori, fingerprintMatch, charges[] | Notification detail |
| `SF86_EXCERPT` | formVersion, submittedDate, section, question | Subject response |
| `DOHA_DECISION` | (existing shape: caseNumber, date, judge, outcome, fullText, sourceUrl) | — |

**Viewer**: `DocumentViewer` becomes a dispatcher keyed on `docType`, with a
per-type layout component (header title/date + provider source chip +
"Received via {provider} · {date}" stamp, KV grid of `fields`, rendered
`sections`, transaction table for SAR). Documents without `docType` (the
existing DOHA record) render via the current DOHA layout, so
`documents/doha-record.json` keeps working unchanged.

**Wiring** (generated data guarantees consistency):
- Every alert's document(s) match its story: DUI alert → Rap Back notification
  (+ police report once "retrieved"); delinquent-debt alert → TransUnion
  credit-file extract; SAR-driven financial alert → FinCEN SAR.
- Alerts change `documentUrl` (single) to `documents: [{ "title", "url" }]`
  (list) — CVTab renders one source-document button per entry.
- Case `documents` tab lists all of the subject's typed documents plus SF-86
  excerpt and any DOHA reference material.
- Hero cases (SUBJ-001..003 and other story subjects) get hand-tuned documents
  in `hero_cases.py`; roster subjects get generated documents for each of their
  alerts and completed record checks.

## 4. Provider provenance everywhere

New shared `SourceChip` component: small pill showing the data-provider name
(with database icon), title-attribute description, linking to `/providers`.
Used in: record-check rows, alert headers (replacing the plain
"Provider: X" text), document viewer header stamp, and the documents tab list.
Provider names in generated data must match `providers.json` names exactly so
the chip can resolve metadata (category, e.g. "Credit bureau (CV provider)").

## 5. Interactive whole-person worksheet (Overview tab)

Case JSON `wholePerson` grows from 4 ad-hoc factors to the **nine SEAD-4
adjudicative-process factors** (¶ 2(d)):

1. Nature, extent, and seriousness of the conduct
2. Circumstances surrounding the conduct
3. Frequency and recency of the conduct
4. Individual's age and maturity at the time of the conduct
5. Extent to which participation is voluntary
6. Presence or absence of rehabilitation and other permanent behavioral changes
7. Motivation for the conduct
8. Potential for pressure, coercion, exploitation, or duress
9. Likelihood of continuation or recurrence

Schema per factor:

```json
{
  "factor": "Frequency and recency of the conduct",
  "assessment": "First incident; very recent (2026-06-21).",
  "evidence": [
    { "type": "ALERT", "ref": "ALERT-201", "label": "Rap Back DUI alert" },
    { "type": "RECORD_CHECK", "ref": "Police report retrieval (2026 arrest)", "label": "Police report retrieval" },
    { "type": "DOCUMENT", "ref": "documents/SUBJ-002/rapback-20260623.json", "label": "Rap Back notification" }
  ]
}
```

**UI** (`WholePersonWorksheet` component replacing the static list):
- Card header: "Whole-person worksheet" + AIBadge + tally chips
  (n favorable / n neutral / n concern) once ratings exist.
- Each factor is an expandable row: AI draft assessment, evidence chips, and —
  for the **adjudicator persona only** — a Favorable / Neutral / Concern
  segmented control plus a note field.
- Evidence chip navigation: `ALERT` → `?tab=continuous-vetting&alert=<id>`;
  `RECORD_CHECK` → `?tab=investigation`; `DOCUMENT` → opens the typed
  DocumentViewer inline under the factor.
- Ratings persist in `DemoContext` (like `roiEntries`):
  `demo.worksheetRatings[caseId][factorIndex] = { rating, note }`, cleared by
  Reset demo.
- Factors with no relevant evidence for clean subjects read "No adverse
  information" with no evidence chips.

## Data generation changes (`portal/data_gen/`)

- `schemas.py`: add document envelope + per-type field schemas, `recordChecks`,
  alert `documents[]`, 9-factor `wholePerson` with `evidence[]`.
- New `documents.py`: builders per docType (realistic agencies, report numbers,
  narratives seeded deterministically per subject).
- `hero_cases.py`: hand-tuned record checks, documents, and worksheet evidence
  for the hero subjects (Okafor financial/foreign-influence story with SAR +
  credit extract; Bell DUI story with Rap Back notice + police report + court
  status; etc.).
- `roster.py` / `generate_demo_data.py`: generate consistent documents +
  record checks + worksheet entries for the remaining subjects; write document
  files into `public/data/documents/<id>/`.
- `tests/`: schema round-trip tests — every alert `documents[].url` and
  record-check `documentUrl` resolves to a generated file; provider names ⊆
  `providers.json`; 9 factors per subject.

6. Subjects home page + routing/nav change
