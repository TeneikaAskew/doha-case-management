# Data Provider Drill-Down - Design Spec

**Date**: 2026-07-04
**Status**: Approved (brainstorming complete)
**Builds on**: `2026-07-03-subject-centric-whole-person-design.md` (typed documents,
record checks, SourceChip provenance) and the portal architecture spec of 2026-07-02.

## Purpose

Make every data provider on the Data Providers page clickable. The detail view
shows the provider's health and reach, a KPI band over the alerts it produced,
a filterable alert table, and the record checks and documents it delivered
across cases - so a stakeholder can walk source → alert → case → document.

**Non-goals**: live provider health simulation; editing providers; alert
disposition from the provider page (that stays on the case CV tab).

## Decisions (locked with user)

| Decision | Choice |
|---|---|
| Investigation-only providers | Detail page has BOTH sections. CV providers show alerts; investigation-only providers (Experian, State & local courts, DMV, IRS, SEAD-5) show a neutral empty alert state ("This source feeds investigations, not continuous vetting") plus their delivered record checks and documents. |
| Data volume | Rich: each of the 7 CV providers ends with 3-6 alerts (~22 new), spread across the CV-enrolled subjects, mostly ADJUDICATED/CLOSED. |
| Association | Canonical `providerId` stamped on every alert by the generator; UI never string-matches provider names. |
| Page architecture | Dedicated route `/providers/:id`, deep-linkable; grid page keeps its cards, now clickable. |

## 1. Data model and generation (`portal/data_gen/`)

### Alert changes
- `CVAlert.providerId: str` - canonical provider id from `providers.json`
  (e.g. `transunion`, `fbi-cjis`). The `provider` display string is unchanged.
  Generator derives `providerId` via one alias map (single source of truth,
  mirroring the UI's `SourceChip` aliases).

### New alerts (~22)
- Target distribution (existing + new = total per provider):
  FBI CJIS 3, Equifax 3, TransUnion 5, LexisNexis 3, FinCEN / Treasury 3,
  CBP I-94 3, DISS 3. Total alerts ≈ 23 (6 today).
- Assigned across CV-enrolled subjects (SUBJ-001, 002, 012, 013, 014, 015),
  3-5 each; every alert's category fits its source:
  credit bureaus → FINANCIAL/CREDIT, FBI → CRIMINAL, CBP → FOREIGN_TRAVEL,
  FinCEN → FINANCIAL, DISS → ELIGIBILITY/SUITABILITY, LexisNexis → SUITABILITY.
- States weighted for believable KPIs: roughly 60% ADJUDICATED, 20% CLOSED
  (false positives), 20% open (NEW/IDENTITY_CONFIRMED/VALIDATED/REFERRED).
- Every new alert satisfies the existing data standards (enforced by tests):
  - at least one typed source document (existing builders; new deterministic
    instances per alert),
  - full `history` phase chain from NEW to its current state with actors/dates,
  - `"<Category> alert received"` (and `... adjudicated` when applicable)
    events on the subject's case timeline, dates consistent,
  - identityMatch/threshold blocks from small per-category templates.
- `SubjectSummary.openAlerts` becomes computed from the subject's alerts
  (count of states not in ADJUDICATED/CLOSED) instead of hand-set, so KPIs,
  cards, and tables stay consistent as data grows.

### New output: `provider-activity.json`
Generated by scanning all cases after assembly:

```json
{
  "providers": {
    "transunion": {
      "alertIds": ["ALERT-101", "..."],
      "recordChecks": [
        { "caseId": "SUBJ-001", "subjectName": "Daniel R. Okafor",
          "item": "Financial record checks", "category": "FINANCIAL",
          "status": "COMPLETE", "completedDate": "2026-03-15",
          "documentUrl": "documents/SUBJ-001/credit-extract-20260620.json" }
      ],
      "documents": [
        { "caseId": "SUBJ-001", "subjectName": "Daniel R. Okafor",
          "title": "TransUnion credit-file extract",
          "url": "documents/SUBJ-001/credit-extract-20260620.json",
          "receivedDate": "2026-06-20" }
      ]
    }
  }
}
```

Record checks match by canonical provider name → id (same alias map);
checks from non-provider sources ("DCSA field operations") are omitted.
Documents are harvested from each case's generated documents by their
`provider` field.

## 2. UI

### Grid page (`DataProviders.jsx`)
- Cards get `card-interactive`, `onClick → navigate('/providers/' + p.id)`,
  keyboard accessible (role="link" behavior via a wrapping button).
- Each card adds one muted activity line: `N alerts · M record checks`
  (from `provider-activity.json` + alerts.json counts; 0 renders as "-").

### Detail page (`pages/ProviderDetail.jsx`, route `/providers/:id`)
Top to bottom:
1. **Header**: back link to Data Providers; provider name (h1), category
   subtitle; health `StatusBadge`; KV strip: record count, last sync,
   used-in pills (Investigation / Continuous Vetting), guideline chips.
2. **KPI band** (house `KPICard`, clickable toggles like the alerts page):
   - Alerts Received (all), Open Alerts, High Severity (open ∩ HIGH),
     Adjudicated / Closed.
   - Counts respect `demo.alertStates` overrides; clicking toggles the
     table filter; active card highlighted.
3. **Alerts table** (`DataTable`): columns Subject, Category, Severity,
   AI Priority, State, Received - same renderers/badge variants as the
   alerts page; category dropdown filter; rows sorted by receivedDate desc;
   row click → `/cases/:subjectId?tab=continuous-vetting&alert=:id`.
   - Investigation-only providers render the neutral EmptyState:
     "This source feeds investigations, not continuous vetting." and no KPI
     band (KPIs would all be zero); the record-check section leads instead.
4. **Record Checks Delivered** card (`DataTable`): Subject, Check, Category,
   Status (badge), Completed, Document ("View in case" link →
   `/cases/:caseId?tab=investigation`). Empty state for providers with no
   checks: "No record checks delivered in the demo data."
5. **Documents Delivered** count folded into the record-check card header
   ("N documents delivered") - no separate table; documents are reachable
   through the checks and alerts that carry them.
6. `SectionRef`: continuous vetting per SEAD 6; record checks per FIS
   (existing `REFS`).
- Unknown `:id` → the standard ErrorAlert ("Provider not found").

### Shared bits
- `useData(getProviderActivity)` added to `data/api.js`
  (`fetchJson('provider-activity.json')`).
- No new visual primitives: KPICard, DataTable, StatusBadge, GuidelineChip,
  SourceChip, EmptyState, SectionRef cover the whole page.

## 3. Testing

- **data_gen tests**:
  - every alert `providerId` ∈ providers.json ids; display string still maps
    through the alias table to the same id;
  - each CV provider has ≥3 alerts; investigation-only providers have 0;
  - `provider-activity.json` validates (new pydantic models), every
    `documentUrl`/alert id resolves, every `caseId` exists;
  - every subject's `openAlerts` equals its computed open-alert count;
  - existing timeline/history/document standards keep passing for the ~22
    new alerts.
- **vitest**:
  - `providerDetail.test.jsx`: KPI math from fixture alerts, KPI toggle
    filtering, category filter, row-click URL, demo-state override changes
    Open count, investigation-only empty state, record-check table + case
    link, unknown id error.
  - `dataProviders.test.jsx`: card click navigates to `/providers/:id`;
    activity line renders.
- **Playwright smoke**: from Data Providers, click TransUnion → KPI band
  visible → click an alert row → case CV tab opens with that alert expanded.

## Implementation order

1. Generator: providerId + alias map, new alert factory + distribution,
   computed openAlerts, provider-activity.json, tests, regenerate.
2. API + ProviderDetail page + route + tests.
3. Grid card click-through + activity line + tests.
4. Smoke test; run full verification; commit/deploy.
